## 3. 改善点(実施済み)

### 3.1 削除(マスク手順 ②)

上表の8モジュール + 各テスト = 16ファイル。`src/` は 39,418 → 37,799 行。
ガムラン/マカームの正規入口は provenance 付きの `getTuningById('slendro-example' / 'pelog-example' /
'makam-ussak-example')` に一本化された。`src/api-surface.test.ts` が削除名13件の**不在を固定**し、
再発を防ぐ。

### 3.2 戻し(マスク手順の "add back")

`pitch-detect.ts` は**残した**唯一の分析系である。調律非依存・埋め込みデータなしで、
measured プリセットの**入力側**(録音 → 調律測定)に対応する。未踏だった分岐を実測して固定:

- **パラボラ補間は実効的**。補間なしでは 44.1kHz で 440Hz は lag 100 = **ちょうど 441Hz**(+3.93c)
  にしかならない。補間で 0.1c 未満に入る。
- **ただし窓長が先**。0.1 秒(110Hz の約11周期)では補間の有無に関わらず約 4.4c ずれる。
  `1/(N-lag)` 正規化が ACF の裾を偏らせるため。精度は「窓長 → 補間」の順で効く。
- **サブハーモニクスへのロックは仕様**。50-60Hz の窓で 440Hz の正弦波を測ると、
  440/8 = **55Hz を確信度 1.0 で返す**。55Hz は実際にこの信号の周期だからで、欠陥ではない。
  窓は「除外したいもの」ではなく「測りたいもの」から決めること。

分岐カバレッジ 85% → 92.5%、行カバレッジ 100%。

さらに `fjs.ts`・`harmonic-entropy.ts` の未踏分岐を同じ手順で掘り、**実バグ1件**を摘出した:

- **`fjsName` が下降音程に存在しない名前を返していた**。FJS の度数は1(ユニゾン)から上に数えるため、
  1未満の比は着地先が無く、演算が音階の下に突き抜けていた — `fjsName(8, 9)` は **`'m0'`**
  (度数0は存在しない)、`fjsName(1, 2)` は `'P-6'`、`fjsName(64, 81)` は `'m-1'`。
  性質記号も誤り(下降長2度なのに `m`)。**下降比は `RangeError` で拒否**し、
  代わりに渡すべき逆比をエラー文に含めるようにした。FJS は上行音程の命名法であり、
  逆方向の記法を勝手に発明しないのが正しい。`ruri info` は既に try/catch していたので、
  今後は無意味な名前を印字せず未注釈になる。

分岐カバレッジ全体 93.67% → **94.04%**、`harmonic-entropy.ts` は穴埋め完了。

### 3.3 第4波: バイナリアダプタ層(`src/adapters/CLAUDE.md` が「I7最高リスク」と宣言する層)

同じ手順を最高リスク層に適用し、**実バグ2件**を摘出した。

- **`decodeSmf` が Program Change / Channel Pressure の後の音符を全て黙って失っていた**。
  両者はデータバイトが**1個**だが、catch-all 分岐が2個進めていた。ストリームがずれ、
  「実機の MIDI ファイルが冒頭で音色を選ぶ」典型的な構成のファイルが、エラーではなく
  **空の音符リスト**にデコードされていた。この制限は docstring に書かれてはいたが、
  **「黙ってデータを失う」ことを文書化しても fail-fast にはならない**。1バイト系を正しく扱い、
  本当に解釈不能なもの(SysEx・System Common の可変長、先行 status の無い running status)は
  推測せず throw するようにした。SMF 仕様どおり meta イベントが running status を打ち切るよう修正。
  `encodeSmf` との golden round-trip は不変。
  なお **running status 自体は正しく動いていた** — `encodeSmf` が常に status を明記するため
  バイト列を手書きしないと踏めず、それゆえ一度もテストされていなかった。
- **`optimalGenerator` がユニゾン目標に対し NaN を黙って返していた**。Tenney 重みは
  `1/log2(num*den)` で、`1/1` の Tenney 高は 0 → ゼロ除算。ガードは存在したが
  `t.num * t.den || 2` と**条件が誤り**(正整数の積は 0 になり得ない。退化するのは積が 1 のとき)。
  検証段階で拒否するようにした。副産物として **`weighting: 'equal'` は実在する設定値**だと確認できた
  (meantone で 696.895c 対 Tenney の 697.378c。各重み付けが各々の誤差尺度を最小化する)—
  先に削除した `maxDegrees` とは異なる。

分岐カバレッジ: `smf.ts` 90.26% → **96.74%**、`ump.ts` 89.06% → **95.31%**、
全体 94.04% → **94.85%**。

### 3.4 第5波: 主張された長所の検算 + CLI 入力の NaN 経路

ソクラテス問答を**長所の側**にも向けた —「主張された長所は本当か?」。

- **「全バイナリアダプタは golden round-trip 検証済み」(`src/adapters/CLAUDE.md`)は MTS で半分だけ真だった**。
  `grep` すると **`mts.ts` にだけ公開デコーダが無い**。往復テストは存在したが、復号ロジックが
  `mts.test.ts` の中に閉じており、パッケージにはフォーマット知識が片方向しか無かった。
  `decodeMts` を公開し、フレーミング・sub-ID・**checksum を検証して不一致は throw** するようにした
  (checksum はこの形式唯一の整合性検査で、これ無しでは1ビット化けたダンプが「もっともらしい調律」に復号される)。
- **`defineTuning` が NaN / Infinity を素通しさせていた** — 「fail fast」が仕事の関数で。
  検査が `referenceHz <= 0` 形で、**NaN との比較は常に false**。結果は CLI まで届いていた:
  `ruri info in.scl --ref abc` は exit 0 でレポートを印字、`ruri convert in.scl -o out.wav --ref abc` は
  **NaN 基準から 132KB の WAV を書いて exit 0**。他3形式は各ライタの周波数検査が偶然拾っていたが、
  エラー文は `frequenciesHz[0]` と的外れだった。`defineTuning` は基準・周期・全度数に有限性を要求し、
  CLI は非数値の `--ref`/`--seconds`/`--limit` を入口で一度だけ、フラグ名を挙げて拒否する。
- 文書化: `scaleToTunText` で MIDI 127 を超える度は**黙って落ちる**(.tun は128鍵固定・残りは12-TET)ことを
  docstring とテストで明記。`kbm.ts` の到達不能な1行(`?? null` の後の `=== undefined` 分岐)を削除。

分岐カバレッジ全体 94.85% → **95.42%**(`cli.ts` 88.9→91.7、`tuning.ts` 94.5→98.4)。公開API 304 → 305。

### 3.7 第8波: エディタに出る主張 — JSDoc `@example` の到達可能性

第7波は README のコード例を検算した。次の問い:
**「`@example` はエディタのツールチップに出る。そこに書かれた API は、消費者が呼べるのか?」**

174個の `@example` から識別子を抽出し、実際の公開 API 305 名と突き合わせた結果、
メソッド名(`.map()` 等)を除いて **25件が「公開 API に存在しない関数」**だった。
`scale.ts` の内部ヘルパ(`progressionNarrative`・`chordMapSummary`・`annotateProgression` …)で、
いずれも `@example` 付きの立派な JSDoc を持つ。

**深いパス import は塞がれている**ことを実測で確認:

```
node -e "import('ruri/core/scale.js')"  →  ERR_PACKAGE_PATH_NOT_EXPORTED
```

`exports` マップのエントリは `ruri` / `ruri/core` / `ruri/adapters` / `ruri/data` の4つのみ。
つまりこの25件は**消費者から到達する手段が存在しない**のに、エディタ上では公開 API のように振る舞っていた。

- **`docs/model-handbook.md` の「パス直指定 import は可能」という記述は誤りだった**。
  第6波で散文のドリフトを直したが、これは**残っていた事実誤認**である(しかも機械生成層は
  削除済みなので二重に古い)。訂正した。
- 25件に `@internal` を付けた。API を広げる(305→330)判断はこの監査の範囲を超えるため、
  **「呼べない API を宣伝しない」**という最小の是正に留めた。内部ヘルパである旨を
  読者と API 抽出ツールの双方に正しく伝える。

**自動化(マスク手順⑤)**: `scripts/check-jsdoc-examples.mjs` を追加。
「`@example` を持つ export は、barrel から到達可能 **または** `@internal`」を強制する。
`prepublishOnly` に配線した(ビルド済み barrel を読むため `check` 本体には入れない — 高速さを保つ)。
**負のコントロール検証済み**: `@internal` を1件削ると exit 1 + 該当関数名、戻すと exit 0。

## 5. この監査から得た運用ルール

1. **ゲートは一箇所にしか無いと迂回される**。データ層に provenance ゲートを置いたなら、
   同種のデータが core に関数として生えていないか定期的に問うこと。
2. **未テスト = 壊れている、と仮定して掘る**。閾値に合わせて数字を足すのではなく、
   未テストの関数・分岐を実際に呼んで検算する。今回までに実バグ2件・要文書化挙動2件が出た。
3. **「使われていない」と「あってはならない」は別の判断**。前者だけなら残す選択もあるが、
   製品自身の不変条件に反するものは、使われていなくても消す。
