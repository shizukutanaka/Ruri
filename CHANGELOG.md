## [0.2.0] - 2026-07-27

Analysis, interoperability and a large subtraction. The public API is
deliberately curated for the first time (1,445 named exports down to 304) and
roughly 225,000 lines of unreachable machine-generated code and its tests are
gone. Nothing the product does was removed — verified from a clean install of
the packed tarball.

**Breaking:** the package no longer re-exports the machine-generated analytics
layer. Every documented entry point, every analysis module and all twelve
presets are unaffected; code importing generated names such as
`tuningFamilyModeParetoFronts` from `'ruri'` must import from the module path
instead, or pin 0.1.0.

### Fixed

- **`tuningHarmonicityProfile` was constant for every tuning, which made `tuningHarmonicityCorrelation` unconditionally `NaN`.** The profile is meant to score each modal rotation of a tuning, and it built those rotations with `scaleMode(tuningToScale(t), k, t)`. But a `Scale` names its notes by _index into the parent tuning_, so rotating the scale that selects **every** degree is a no-op: all `n` rotations come back as the same index set, and therefore the same harmonicity. The Pearson correlation of two constant profiles has zero variance in both terms, so `compareTuningReports(...).correlation` — a documented field, reachable from `comparePresets` — had never returned a number for any input. The profile now rotates in **cents space** (`c[(k + i) mod n] − c[k]`, wrapped by `periodCents`), which is what "mode k" means for an unequal tuning. Pythagorean 12 now profiles as 232560, 6120, 1244880, … instead of twelve copies of one value, and 5-limit just against Pythagorean correlates at 0.456. An **equal** temperament still yields `NaN`, and that is now the correct answer rather than a symptom: every rotation of an equal division genuinely has the same interval set, so its profile has no variance to correlate against — the JSDoc says so, and a test pins it. Neither function had a single test, which is how this survived; both now do.
- **`decodeSmf` silently lost every note after a Program Change or Channel Pressure.** Both carry a _single_ data byte; the decoder's catch-all branch advanced by two. That desynchronises the stream, so a file opening with a Program Change — which is how a real MIDI file picks its instrument — decoded to an empty note list rather than an error. The limitation was documented, but documenting silent data loss is not the same as failing loudly, and this decoder is publicly exported. One-data-byte messages are now handled, and the cases that genuinely cannot be parsed throw instead of guessing: SysEx and System Common are variable-length and refused, as is running status with no preceding channel status. Meta events now cancel running status per the SMF specification, so a running-status note event after a meta event is read as a note rather than as more meta. The golden round-trip with `encodeSmf` is unchanged. Running status itself — a documented feature of this decoder — turned out to work correctly and now has the test it never had; it can only be reached by hand-assembling bytes, since `encodeSmf` always writes explicit status bytes, which is why the whole area went unexercised.
- **`optimalGenerator` returned NaN for a unison target instead of rejecting it.** Tenney weight is `1/log2(num*den)`, and the unison's Tenney height is zero, so `1/1` divided by zero and every field of the result came back NaN — silently. A guard was present but tested the wrong condition: `t.num * t.den || 2` catches a product of zero, which positive integers cannot produce, while the degenerate case is a product of one. The unison is now rejected at validation, where it belongs: there is nothing about `1/1` to approximate. This also confirmed the `weighting: 'equal'` option is real, unlike the `maxDegrees` parameter removed earlier — it picks 696.895c against Tenney's 697.378c for meantone, and each weighting minimises its own error measure.
- **`fjsName` returned names that do not exist for descending ratios.** FJS degree numbers count upward from 1 (unison), so a ratio below 1 had nowhere to land and the arithmetic ran off the bottom of the scale: `fjsName(8, 9)` returned `'m0'` — there is no degree zero — `fjsName(1, 2)` returned `'P-6'`, and `fjsName(64, 81)` returned `'m-1'`. The quality letter was wrong too (`m` for what is a major second taken downward). Descending ratios are now rejected with a `RangeError` that names the inverted ratio to pass instead, which is the honest answer: FJS specifies names for ascending just intervals and invents nothing for the other direction. `ruri info` already guarded this call, so it now leaves such a degree unannotated rather than printing nonsense.
- **`bestModeForTuning`'s `maxDegrees` parameter could not do what it claimed.** It was documented as limiting the search space for large tunings, but both rankings it delegates to operate on `scaleModeSeries`, whose rotations all have exactly as many degrees as the tuning. So `maxDegrees >= n` filtered nothing and `maxDegrees < n` filtered everything and threw: no setting narrowed a result. Removed; no caller ever passed it. The empty-tuning guard it used to carry is kept, now with an accurate message instead of "no modes satisfy the maxDegrees constraint".
- **Nine public functions had no test at all** and were only found by chasing the function-coverage gate: `closestPreset`, `closestPresetTuning`, `allPresetReports`, `comparePresets`, `bestModeWav`, `tuningToFullBundle`, `bestProgressionForScale`, `singleBestChord` and `bestModeForTuning`. **Function coverage is now 100%.** Writing the tests turned up a second piece of misinformation — `tuningToFullBundle`'s `name` option is documented as changing the TUN map, but it only switches the TUN writer to an explicit `anchorMidiNote: 69`, which is already the default, so only the MTS bulk-dump name actually differs. The test now pins the real behaviour.
- **devDependency vulnerabilities: 10 → 0.** `npm audit` reported 2 critical, 5 high and 3 moderate, all reachable only through the vitest 2 toolchain (vitest, vite, esbuild, postcss, nanoid). vitest 4 fixes them. The upgrade was previously deferred as risky because it would "break the test split" — but that split was deleted, so the reason no longer existed.
- **`src/adapters/wav.ts`: 2,284 → 439 lines.** The vitest 4 upgrade enforced a 5-second default test timeout that vitest 2 had let slide, which failed seven tests taking 7–26 seconds each. They turned out to be rendering audio for `tuningModeProgressionWavBundles` and `tuningFamilyProgressionWavBundles` — generated analytics called from nowhere outside the module and its own test. Applying the same reachability closure kept 16 of 57 exports. The fix for the timeout was deletion, not a larger timeout.
- As a direct consequence, **`npm run check` went from 1m34s to 18 seconds** (tests 82s → 6.9s). Accelerating the cycle came free from deleting the part, which is the order Musk's algorithm prescribes.

- **The coverage gate now measures the project rather than the generator.** It demanded 80% and read ~36%, so it had never passed and was documented as "do not use for pass/fail". The cause was not a strict threshold but a wrong denominator: `include` counted the 128,000 lines of machine-generated implementation. Measured over hand-written code alone, coverage is **98.18% lines, 94.58% branches, 100% functions, 98.18% statements**, with no file below 80%. The generated implementations are excluded (they are not public API and their generated suites are gone), and the thresholds were **raised** to 95/90/98/95 — a real gate with headroom, not a lowered bar.

### Removed

- **Eight core modules that violated the project's own invariants — `gamelan`, `key-detect`, `tonnetz`, `pcset`, `maqam`, `japanese-scale`, `progression`, `rhythm`.** The data layer enforces provenance — a `source: 'measured'` preset cannot load without citation, license, cultural context and region — but that gate lives only in `src/data`. The same kind of data had grown in `src/core` as plain functions, where nothing checked it. `gamelanTuning` was the clearest case: five ethnic tuning tables with no citation at all, duplicating the gated `SLENDRO_EXAMPLE`/`PELOG_EXAMPLE` **and doing it worse** — it forced an exact 1200c octave, flattening the measured stretched pseudo-octave (1208c) that `tuning.ts` itself documents as the reason tunings have no single normal form. `detectKey` implemented Krumhansl-Schmuckler probe-tone profiles, which are Western listener _enculturation_ data — precisely the "familiarity" axis the README says is deliberately excluded. `tonnetz` (neo-Riemannian PLR) and `pcset` (Forte set classes) are 12-TET Western analysis by construction, and `forteNumber` shipped 12 entries of a 208-entry catalogue with a test that froze the gaps as correct. `maqam` and `japanese-scale` quantised living traditions onto 24-EDO and 100-cent grids and called it educational. `rhythm` (euclidean patterns) never mentions pitch at all. Every one of them had no importer outside the barrel and its own test, and none appeared in the README. `src/` drops 39,418 → 37,799 lines and the public surface 328 → 304. `src/api-surface.test.ts` pins the thirteen removed names as absent so they cannot come back unnoticed. Full reasoning in `docs/audit-2026-08.md`.
- **The unreachable generated implementation — 119,000 lines.** Curating the public API and deleting the generated tests exposed the real question: how much of `scale.ts` and `presets.ts` is reachable at all? Computing the transitive closure from the curated barrels, the CLI and the hand-written adapters gave the answer: **440 of 3,711 declarations in `scale.ts` and 32 of 2,206 in `presets.ts`**. The rest was reachable only from itself. The closure was run to a fixed point — the first pass over-approximated by matching identifiers inside JSDoc comments, and re-running it with comments stripped removed a further 96 declarations that only ever appeared in prose. `scale.ts` is now 4,759 lines (was 80,234) and `presets.ts` 702 (was 38,695); `src/` drops from 186,604 to **39,247 lines**. Tests that existed solely to exercise the deleted code went with it (7,485 → 2,833), and `presets.test.ts` disappeared entirely because every test in it targeted generated functions. Nothing the product does changed: the CLI, every adapter, all twelve presets and all 304 public exports behave identically, verified from a clean `npm install` of the packed tarball.
- With the bulk gone, the coverage gate no longer needs its carve-out: **every file under `src/` is measured**, at 98.19% statements / 94.85% branches / **100% functions** / 98.63% lines against thresholds of 95/90/98/95.

- **99,237 lines of machine-generated tests** (`scale-generated.test.ts`, `presets-generated.test.ts` — 12,311 cases). They were excluded from `test`, from `lint` and from `coverage`, so the only way to run them was a manual script taking roughly five hours; in practice they never ran. A test that never runs provides no protection, only the appearance of it, and the hand-written suites already contribute 5,797 cases over the same modules. Deleting them let the workarounds go too: `test`, `lint` and `coverage` no longer carry `--exclude`/`--ignore-pattern` flags, and the `test:generated` script is gone. The test count is unchanged at 7,485, which is the proof they were contributing nothing.

### Changed

- **The public API is now curated.** The package re-exported 1,445 explicitly named symbols while the README documented 56 — a 26:1 ratio that made the library unsearchable, since anyone looking for `edo` had to find it among names like `tuningFamilyAmbassadorConsensusConvergenceScoreNarrative`. The barrels now offer a deliberate surface: 304 exports, covering every documented entry point, every analysis module, and every curated preset. **No implementation was removed** — the machine-generated analytics layer is untouched and still importable from its module by path; what changed is what the package _offers_. `src/api-surface.test.ts` pins this: every documented symbol must resolve, and the surface must not silently grow back.

### Added

- Two 1/6-comma circulating well-temperaments, taking the curated catalogue to 12: `vallotti` (six white-key fifths F–C–G–D–A–E–B narrowed, favouring C major) and `young-ii` (the same six narrowed fifths shifted one step sharpward to C–G–D–A–E–B–F♯, favouring G major). Both are **derived from their construction rather than transcribed from a table**, so the defining property is checkable: twelve fifths close into exactly seven octaves, six narrowed by precisely one sixth of the Pythagorean comma (698.045c) and six pure. The attribution of the two layouts is genuinely disputed in the literature — see Duffin, "Why I hate Vallotti (or is it Young?)" — so each preset is named by its construction and records the dispute in its `note` rather than silently picking a side.
- Scale Workshop scale-data import (`src/adapters/scale-workshop.ts`): `parseScaleWorkshop` and `parseScaleWorkshopLine`. Scale Workshop is the browser tool xenharmonic composers actually use, and its one-interval-per-line "scale data" box is the informal lingua franca scales get pasted around in; this reads it directly, without a detour through `.scl`. All four line forms are supported — ratios (`3/2`, `2`), cents (`701.9`, `1200.`), EDO steps (`7\\12`) and decimal ratios (`1.5e`, `14e-1`) — with the discriminators applied in a fixed order, since `1.5e` carries both a dot and an `e`. The decisive rule is that **a dot is what makes a line cents**: `2` is the ratio 2/1 while `2.` is two cents, a factor-of-600 difference, and a test pins it. Ratios are kept as ratios rather than flattened to cents, so imported just intervals stay exact. `ruri info` and `ruri convert` now accept `.txt`/`.sw` input alongside `.scl`. Reference: Scale Workshop user guide; github.com/xenharmonic-devs/scale-workshop.
- Just-interval naming in the Functional Just System (`src/core/fjs.ts`): `fjsName` and `fjsFormalComma`. `interval-name.ts` names the steps of an equal division; this names exact just ratios, the other half of writing a tuning down. Classical names come from the chain of fifths and so reach only 3-limit intervals — 81/64 and 5/4 are both "major thirds" 21.5 cents apart — so FJS keeps the Pythagorean name and marks the difference with an accidental naming the responsible prime: `81/64` stays `M3` while `5/4` becomes `M3^5`, `6/5` is `m3_5`, `7/4` is `m7^7`. The accidentals are derived, not tabulated: the FJS master algorithm walks the chain of fifths outward and takes the first Pythagorean interval within the radius of tolerance (65/63, the mediant of 33/32 and 32/31). It reproduces the known formal commas — 80/81 for prime 5, 63/64 for 7, 33/32 for 11, 1053/1024 for 13 — and the radius is self-validating, admitting 33/32 while excluding 32/31, which is exactly why that mediant was chosen. `ruri info` now names exact-ratio degrees. Reference: "The Functional Just System" (misotanni.github.io/fjs); Xenharmonic Wiki, "Functional Just System".
- Generator tuning optimisation (`src/core/generator-tuning.ts`): `optimalGenerator` and `generatorError` answer the number left over once `val.ts` has identified a temperament and `mos-spectrum.ts` has given its viable scale sizes — how wide the generator should actually be. A rank-2 temperament maps each just ratio to `a` periods plus `b` generators, so with the period held pure the choice is a one-dimensional weighted least-squares problem with a closed-form solution (`g* = Σ w²b(t − aP) / Σ w²b²`) — no search, no matrix inversion, no dependency. Weights default to Tenney's `1/log₂(n·d)`. Self-checking against known tunings: optimising for 3/2 alone returns the pure fifth (701.955c), and for 5/4 alone returns 696.578c — quarter-comma meantone — which `temperament.ts` derives independently as `3/2 − syntonic/4`. `MEANTONE_5_LIMIT` ships the 5-limit meantone mapping; its Tenney-optimal fifth is 697.378c, beating 12-EDO's 700c, the pure fifth and quarter-comma on weighted RMS. References: Paul Erlich, "A Middle Path"; Xenharmonic Wiki, "Target tunings" / "Tenney-Euclidean temperament measures" (this implements the pure-octave least-squares case those generalise).
- MOS spectrum (`src/core/mos-spectrum.ts`): `mosSizes` and `mosSpectrum` answer which scale sizes a generator is worth building at — the predictive counterpart to `tuningMosPattern`, which could only judge a scale after the fact. A pure fifth returns the classic ladder `[2, 3, 5, 7, 12, 17, 29, 41, 53]` (why the chain of fifths gives 5-, 7- and 12-note scales and not 6 or 8); a golden-ratio generator returns the Fibonacci numbers, with L/s counts that are themselves consecutive Fibonacci pairs (`3L2s`, `5L3s`, `8L5s`, `13L8s`). Rather than reimplementing continued fractions, it applies the definition and reuses the library's own `isWellFormed`, so prediction and verdict cannot disagree. That choice is load-bearing: testing merely for "two step sizes" reports _every_ size from 2 to 60 as MOS for an exact 700c fifth, whereas Myhill's property correctly stops at 11, where a 12-note stack collapses into 12-EDO. `ruri mos <generatorCents> [<periodCents>]` prints the ladder with each size's L/s pattern. References: Erv Wilson, "Introduction to the Moments of Symmetry" (1975); Xenharmonic Wiki, "Mathematics of MOS".
- Interval naming in ups-and-downs notation (`src/core/interval-name.ts`): `edoFifthSteps`, `edoSharpness`, `edoIntervalName`, `edoIntervalNames`. The library could measure intervals but not say what they are _called_; this names every step of any EDO using conventional qualities (perfect/major/minor/augmented/diminished) from the chain of fifths, filling the gaps classical names cannot reach with `^`/`v` arrows of one step. Sharpness (`7·fifth − 4·n`) classifies the whole system: 1 for 12/19-EDO (classical names suffice), 0 for the perfect EDOs 7/14/21/28/35 (major equals minor), negative for the superflat EDOs 9/11/16/23 (major is _narrower_ than minor), ≥2 where arrows become the intended mechanism. Verified against the published classifications and against 12-EDO reproducing exactly `P1 m2 M2 m3 M3 P4 A4 P5 m6 M6 m7 M7 P8`. `ruri edo` now prints the sharpness, its character, and the full interval-name list. Reference: Xenharmonic Wiki, "Kite's ups and downs notation"; Kite Giedraitis, "Notation Guide for EDOs 5-72".
- Harmonic entropy (`src/core/harmonic-entropy.ts`), a third and independent axis of consonance: `entropyBasis`, `harmonicEntropy`, `harmonicEntropyCurve`. Where roughness measures beating between partials (timbre-dependent) and Stolzenburg periodicity measures exact waveform repetition (brittle — 3/2 is maximally periodic but 300/201 is not, though no ear could tell them apart), harmonic entropy measures how _confidently_ an interval is heard as one simple ratio. It is tolerant of mistuning by construction and **takes no spectrum**, because it models pitch interpretation rather than partial interaction. Verified by scanning the curve: its minima land on 6/5, 5/4, 4/3, 3/2, 5/3 and 7/4 with no spectrum supplied, and unison/octave score as the most certain intervals. `ruri info` now shows per-degree entropy. Reference: Paul Erlich, harmonic entropy (Xenharmonic Wiki; Tonalsoft).
- Timbre design for a given scale (`src/core/induced-spectrum.ts`): `inducedSpectrum` builds a spectrum whose partials land on a tuning's own pitches — the inverse of the existing `spectrumToTuning`, completing the library's central thesis that consonance is a property of the (spectrum, tuning) pair rather than of intervals in the abstract. `spectrumBendCents` reports how far a harmonic timbre must move to fit a tuning, which is also a measure of how much the technique has to offer it. Verified to reproduce the effect Sethares describes: the induced timbre lowers mean step dissonance in every EDO tested, the gain is larger for EDOs that fit the harmonic series poorly (13-EDO, 90c bend) than for those that fit it well (12-EDO, 18c bend), and under its own timbre 13-EDO nearly closes the consonance gap with 12-EDO. Reference: W. A. Sethares, _Tuning, Timbre, Spectrum, Scale_ (2nd ed.).
- `--fit-timbre` flag for `.wav` output (`convert`/`gen`/`presets`): synthesize the scale with the timbre designed for it (modal synthesis over the induced spectrum) instead of a generic plucked string, making the effect audible. `ruri edo` also reports the timbre bend.
- Vals and tempered-out commas (`src/core/val.ts`): `patentVal` (an EDO's nearest step-count per prime, e.g. 17-EDO → `<17 27 39]`), `mapRatioByVal` (any ratio's step-count, turning interval arithmetic into integer addition), `tempersOut` and `temperedCommas` (which commas vanish — the exact test that _identifies_ a temperament: an EDO tempering out 81/80 is a meantone system, one tempering out 250/243 is porcupine). Unlike the proximity-based `nearestComma`, this is exact integer arithmetic on prime exponents with no tolerance parameter. Verified against published values: 17-EDO's patent val, the classic meantone EDOs (12/19/26/31/43/50) versus the standard non-meantone counterexamples (15/17/22/53), porcupine as the 15 & 22 temperament, 12-EDO closing the circle of fifths via the Pythagorean comma, and 53-EDO as a schismatic system. Reference: Xenharmonic Wiki "Val"/"Patent val"; Erlich, "A Middle Path".
- `ruri edo` now also prints the patent val and the commas the EDO tempers out, so it names the temperament family rather than only scoring accuracy.
- Just-intonation approximation metrics (`src/core/edo-error.ts`), the standard regular-temperament-theory answer to "is this EDO any good?": `relativeError` (error as a fraction of one EDO step, comparable across EDOs in a way absolute cents are not), `edoHarmonicErrors` (per-odd-harmonic error table), `isConsistent` / `edoConsistencyLimit` (the 25%-of-a-step consistency criterion). Verified against published results — 46-EDO is the smallest EDO consistent in the 13-odd-limit, 12-EDO reaches the 5-odd-limit, 41-EDO the 11th — plus the textbook figures for 12-TET's 13.7c-sharp third and 2c-flat fifth. References: Xenharmonic Wiki "Relative interval error"/"Consistency"; Erlich, "A Middle Path".
- `ruri edo <divisions> [--limit <oddLimit>]`: prints an EDO's step size, consistency limit, and per-harmonic error in both cents and percent-of-a-step.
- Five historical/theoretical tuning presets, doubling the curated catalogue from 5 to 10: `pythagorean-12` (3-limit, stored as exact ratios), `meantone-quarter-comma` (Aron 1523), `werckmeister-iii` (1691), `kirnberger-iii` (1779), and `bohlen-pierce-13` (13 equal divisions of the 3/1 tritave — a non-octave period). Each carries full provenance and is covered by an independent verification oracle: agreement with the library's own construction (`meantoneQuarterComma`, `edo` over a tritave), or the temperament's defining published property (Kirnberger III's pure 5/4 third; Werckmeister III's 390.225c third sitting between just and 12-TET; Pythagorean's degrees being exclusively 2-and-3-limit ratios). These are `source: 'theoretical'` and therefore outside the CARE/OCAP gate, which `loadTuningPreset` applies only to `source: 'measured'` data — see `docs/first-principles-2026-07.md`.
- `ruri presets`: list the curated tunings with their citations, or export one by id (`ruri presets kirnberger-iii -o k3.scl`) in any convert format. Curated preset data was previously unreachable from the CLI.
- `--name <text>` option for `convert`/`gen`/`presets`, overriding the name/id written into the output tuning.
- `ruri convert`/`ruri gen` now accept `.wav` output, so a generated tuning can be auditioned directly (`ruri gen edo 19 -o 19edo.wav`) without a separate `.scl`-then-`render` step. `--seconds` sets the per-note duration. The format-writing dispatch (`writeTuningOutput`) that both commands share gained the `.wav` case via `tuningToScaleWav`.
- `ruri info` now annotates cents-based degrees with the nearest simple just ratio (e.g. `386.3137c … ≈ 5/4 (+0.0c)`), a display-only hint gated on ≤ 1.0c error and odd-limit ≤ 15 so it labels genuine JI — and genuinely near-just tempered degrees such as 19-EDO's 6/5 minor third — while leaving ordinary tempered/irrational steps unlabeled. It is an approximation hint (marked `≈`), never a cents→ratio conversion.
- `ruri gen <edo N | mos g p c | me c d> -o <output>`: generate a tuning from theory with no input file — n-EDO (`edo`), a generated/MOS scale (`mos <generatorCents> <periodCents> <count>`), or a maximally-even set (`me <chromaticSteps> <notes>`) — and write it in any of the same formats `convert` supports (`.scl`/`.tun`/`.syx`/`.ump`/`.mid`). Exposes the library's generation layer (`edo`, `generatedTuning`, `maximallyEvenTuning`) on the command line for the first time. The format-writing dispatch is now shared between `convert` and `gen`.

### Fixed

- `mosPattern`/`isWellFormed` step-size quantization coarsened from 1e-6 to 1e-3 cents (`src/core/generate.ts`). The old grid was as fine as the 6-decimal cents a `.scl` file stores, so a `.scl` round-trip's sub-milli-cent noise split one true step size into spurious classes — misreporting an equal division (e.g. 19-EDO) as an irregular MOS and as "well-formed". 0.001c is still 1000× below perception yet immune to that noise; the two functions continue to share the constant so they stay mutually consistent.

- `ruri convert -o <file>.mid` now writes a valid, playable Standard MIDI File (a one-note-per-degree melody via `scaleToSmf`) instead of raw MTS SysEx bytes, which produced a file that was not a valid SMF (no `MThd` header) and that DAWs reject. Raw MTS SysEx remains available as `.syx`. Because a plain SMF carries only integer note numbers, `.mid` conversion prints a warning to stderr with the maximum 12-TET rounding error when the tuning is microtonal, pointing to `.ump`/`.syx`/`.tun` for exact-pitch export.

## [0.1.0] - 2026-07-14

### Added

- Core tuning engine: cents/ratio pitch model, tuning systems with non-octave periods, fail-fast invariants.
- Idiom-independent scale/chord generation (MOS, well-formed test, maximally even sets).
- Consonance evaluation: Plomp-Levelt/Sethares roughness + Stolzenburg harmonicity (acoustic-only, timbre-dependent).
- Instrument spectra (harmonic / stretched / bell) as single source of truth for scoring and synthesis.
- Fingering for fretted instruments (guitar, bass) with biomechanical cost, per-player HandProfile, K-best; piano finger assignment.
- Synthesis: Karplus-Strong plucked string, modal additive synthesis (inharmonic timbres). Microtonal via fractional delay / detune.
- Output adapters: Standard MIDI File (SMF Type-0), Scala `.scl` (bidirectional), MPE, WAV.
- Curated tuning presets with provenance and cultural context (12-TET, 5-limit JI, Makam Uşşak, Sléndro, Pélog) under CARE/OCAP principles.
- Single-file web demo UI (tuning → chord → consonance → fingering → audition → export).
- `edo(divisions, referenceHz?, periodCents?)`: n-tone equal division of the octave (or any period) as a first-class `TuningSystem`.
- MTS adapter (`src/adapters/mts.ts`): `freqToMtsKey`, `mtsBulkDump` (MIDI Tuning Standard non-real-time bulk dump SysEx, 408 bytes), `tuningToMtsFrequencies` — maps a `TuningSystem` onto all 128 MIDI keys for DAW/synth retuning.
- `.kbm` adapter (`src/adapters/kbm.ts`): `parseKbm`, `writeKbm`, `kbmNoteToFreq` — Scala keyboard mapping; unmapped keys (`x`) return `null`.
- npm packaging: `npm run build` emits ESM + `.d.ts` to `dist/` via `tsconfig.build.json` (NodeNext modules); `package.json` exports map (`"."` / `"./core"` / `"./adapters"` / `"./data"`), `types`, `files`, `prepublishOnly` hook; top-level barrel `src/index.ts`.
- Regular temperaments (`src/core/temperament.ts`): `regularTemperament` (generator-stacked tunings, non-octave periods supported), `meantoneQuarterComma` (pure 5/4 major third), `pythagorean` (pure 3/2 fifths).
- Chord discovery (`src/core/chord-search.ts`): `rankChords` enumerates degree subsets of a tuning and ranks them by Sethares roughness + Stolzenburg periodicity (acoustic-only, timbre-dependent).
- `.tun` adapter (`src/adapters/tun.ts`): `writeTun` — AnaMark TUN text export (`[Tuning]` + `[Exact Tuning]` sections); composes with `tuningToMtsFrequencies`.
- `consonantIntervals(spectrum, opts?)` (`src/core/dissonance.ts`): the library's timbre-dependent-consonance thesis as one call — scans the sensory-dissonance curve and returns its local minima as `{ ratio, cents, dissonance }`. A harmonic spectrum yields the just intervals (4/3, 3/2, 5/4…); `bellSpectrum()` yields a different set from the very same scan.
- `generatedTuning(generatorCents, periodCents, count, referenceHz?, id?)` and `maximallyEvenTuning(c, d, periodCents?, referenceHz?)` (`src/core/generate.ts`): bridge `generatedScale`/`maximallyEven` to a first-class `TuningSystem`, closing the abstraction gap between the MOS/ME generators and the rest of the pipeline (`rankChords`, `mtsBulkDump`, `fingerChord`, etc.).
- `scaleToFreqs(scale, tuning)` (`src/core/scale.ts`): absolute Hz for each scale step — the bridge from the melodic/modal `Scale` layer into the frequency world (`chordDissonance`, `pluck`, `strike`, MTS/`.tun` export). The `Scale` module also gains a dedicated test suite (`scale.test.ts`).
- `realizeRankedChordFreqs(chord, rootHz)` (`src/core/chord-search.ts`): realize a `RankedChord` as absolute Hz — the bridge from the ranking layer into the frequency world (`voiceLeadingCost`, `chordDissonance`, synthesis). Closes the pipeline: `generatedTuning → rankChords → realizeRankedChordFreqs → voiceLeadingCost`.
- `chordToCentOffsets(chord, rootCentsOnInstrument)` (`src/core/chord.ts`): bridge from `Chord` (root-relative intervals) into the instrument coordinate system that `fingerChord` speaks. `StringInstrument` has no Hz anchor by design (instruments are transposable); this helper supplies the root position in instrument-local cents. New dedicated `chord.test.ts`.
- `progressionSmoothness(chords, rootHz)` (`src/core/chord-search.ts`): total minimal voice-leading cost across a chord progression (3+ chords) as a single call. Aggregates pairwise `voiceLeadingCost` over consecutive pairs, enabling the full DTM workflow: `generatedTuning → rankChords → progressionSmoothness`.
- `getTuningById(id, presets?)` (`src/data/presets.ts`): look up a curated preset by id string and return a validated `TuningSystem` (or `undefined`). Replaces the two-step `import MAKAM_USSAK; loadTuningPreset(MAKAM_USSAK)` pattern with a single discoverable call. Default pool is `ALL_PRESETS`; a custom pool can be supplied.
- Integration tests (`src/integration-extended.test.ts`): end-to-end pipeline tests for Q31-Q36 bridging functions used together — Makam preset through full pipeline, Chord → fretless oud fingering, EDO progression smoothness across 7/12/19-EDO.
- `chordFromRatios(name, ratios)` (`src/core/chord.ts`): build a just-intonation chord from integer ratio pairs, storing intervals as `{kind:'ratio'}` (primary representation, no cents conversion). Closes the gap between the "ratio is primary" design principle and the `Chord` factory API. `chordFromSemitones` only created cents-based intervals; `chordFromRatios` preserves exact JI precision through `realizeChordFreqs`.
- `scaleMode(scale, modeIndex, tuning)` (`src/core/scale.ts`): modal rotation as a first-class `Scale` operation. Rotated pre-pivot degrees are shifted up by one period (`tuning.degrees.length`), so non-octave tunings work. Invariant: step-size multiset preserved across all rotations.
- `rankedChordToChord(ranked, name?)` (`src/core/chord-search.ts`): lift a `RankedChord` (tuning-discovery output) to a portable `Chord` (root-relative intervals). `RankedChord.cents` are already root-relative so this is a direct lift — no arithmetic. Closes the round-trip `rankChords → rankedChordToChord → Chord → fingerChord / writeScl / realizeChordFreqs`.
- `scaleToTuning(scale, tuning)` (`src/core/scale.ts`): promote a `Scale` (degree-selection descriptor) to a full `TuningSystem` containing only those selected degrees. Enables diatonic chord discovery: `rankChords(scaleToTuning(dorianScale, t12))` returns only triads from Dorian's 7 degrees (C(6,2)=15 candidates) rather than all 12-TET triads (C(11,2)=55). Composes naturally with `scaleMode`: `scaleMode → scaleToTuning → rankChords` gives per-mode diatonic harmony.
- `tuningToScale(tuning, name?)` (`src/core/scale.ts`): create a `Scale` spanning all degrees of a `TuningSystem`. Bridges the generation layer to the modal layer: `tuningToScale(generatedTuning(700,1200,7))` returns a Scale that can be passed to `scaleMode`, `scaleToTuning`, or `scaleToCents`, closing the pipeline: `generatedTuning → tuningToScale → scaleMode → scaleToTuning → rankChords`. Round-trip invariant: `tuningToScale(t) → scaleToTuning(…,t)` recovers the original cents.
- `scaleDissonance(scale, tuning, spectrum)` and `rankModes(scale, tuning, spectrum)` (`src/core/scale.ts`): bridge between the modal layer and the acoustic evaluation layer. `scaleDissonance` scores all scale degrees sounding simultaneously; `rankModes` ranks all rotations of a scale by dissonance (ascending), returning `RankedMode[]`. Timbre-dependent: swapping the spectrum changes the modal ranking — the library's core thesis applied at the scale level.
- `spectrumToTuning(spectrum, opts?)` (`src/core/dissonance.ts`): derive a `TuningSystem` from a timbre's consonant intervals — the capstone of the library's "consonance is timbre-dependent" thesis. `spectrumToTuning(harmonicSpectrum())` returns a tuning containing just intervals (5/4, 4/3, 3/2…); `spectrumToTuning(bellSpectrum())` returns an acoustically different set. The result plugs into the full pipeline: `rankChords`, `mtsBulkDump`, `tuningToScl`, `fingerChord`.
- `chordFromDegrees(tuning, degreeIndices, name?)` (`src/core/chord.ts`): tuning-aware chord factory. `chordFromSemitones` implicitly assumes 12-TET (1 semitone = 100c); for 19-EDO, Makam, or any other tuning, this factory looks up exact degree cents and produces root-relative intervals automatically. `chordFromDegrees(equalTemperament12(440), [0,4,7])` equals `chordFromSemitones('major', [0,4,7])` (verified by test).
- `tuningToScl(tuning)` (`src/adapters/scala.ts`): direct adapter from `TuningSystem` to Scala `ScalaScale`. JI ratio degrees are preserved as ratio text (`5/4`) — not lossy cents — enabling lossless `writeScl → parseScl` round-trips. Non-octave periods (Bohlen-Pierce 1902c) are written correctly as the final entry. Composes with `writeScl` for one-liner `.scl` export.
- `scaleMode(scale, modeIndex, tuning)` (`src/core/scale.ts`): modal rotation as a first-class `Scale` operation — returns the scale starting from degree `modeIndex`, re-zeroed to 0-based indices. Rotated degrees prior to the pivot are shifted up by one period (`tuning.degrees.length`), so non-octave tunings (Bohlen-Pierce, stretched gamelan) work correctly. Invariant: the multiset of step sizes is preserved under all rotations. Closes the gap between "Scale is first-class for maqam/raga" and the absence of modal rotation.
- `pluckChord(freqs, opts?)` (`src/core/ks-synth.ts`): synthesize a chord of N notes with Karplus-Strong in one call. Closes the pipeline: `realizeRankedChordFreqs → pluckChord → encodeWav`. Previously required `mix(freqs.map(f => pluck(f, opts)))`.
- `strikeChord(freqs, spectrum, opts?)` (`src/core/modal-synth.ts`): synthesize a chord of N notes with modal (additive) synthesis in one call. Uses the same spectrum as `chordDissonance` — single source of truth for timbre. Closes the parallel pipeline for inharmonic instruments (gamelan, bells).
- `isTuningWellFormed(tuning)` (`src/core/generate.ts`): test whether a `TuningSystem` satisfies Myhill's property (well-formed / MOS). Bridges `isWellFormed(number[], period)` to the `TuningSystem` type. `generatedTuning(700,1200,7)` → true; `maximallyEvenTuning(12,6)` (whole-tone) → false. Non-octave periods supported.
- `chordProgressionSmoothness(chords, rootHz)` (`src/core/chord-search.ts`): total minimal voice-leading cost across a `Chord[]` progression (the portable representation). Mirrors `progressionSmoothness` but accepts `Chord[]` returned by `rankedChordToChord`, closing the round-trip: `rankChords → rankedChordToChord → chordProgressionSmoothness`. Identical cost to `progressionSmoothness` on the same data (verified by test).
- `optimalChordOrder(chords, rootHz)` (`src/core/chord-search.ts`): find the permutation of `Chord[]` that minimises total voice-leading cost. For n ≤ 8 uses Heap's algorithm for exact global optimum (40320 max iterations); for n > 8 uses nearest-neighbour heuristic with all starting points. Returns `OptimalProgressionResult` with the reordered chords, original-index permutation, and totalCents. Closes the gap between `progressionSmoothness` (measuring cost) and actually optimising the order.
- `isScaleCompatible(scale, tuning)` (`src/core/scale.ts`): public predicate form of the internal `assertTuningMatch` guard. Returns `true` iff `scale.tuningId === tuning.id` and all degree indices are in `[0, tuning.degrees.length)`. Allows callers to validate dynamically-constructed `Scale` objects before passing them to functions that would throw.
- `voicesForChordObject(chord, rootHz, spectrum, gain?)` (`src/core/synth.ts`): bridge from the portable `Chord` type directly into Web Audio `Voice[]` in one call. Equivalent to `voicesForChord(realizeChordFreqs(chord, rootHz), spectrum, gain)`, closing the last abstraction gap in the synthesis chain: `chordFromSemitones → voicesForChordObject → schedule OscillatorNode`.
- `tuningSuitability(tuning, spectrum, opts?)` (`src/core/dissonance.ts`): the inverse of `spectrumToTuning` — measures how well an _existing_ tuning system covers the consonant intervals of a given timbre. Returns `{ coverage, avgErrorCents, totalConsonantIntervals, matchedCount }`. `coverage` is the fraction of the timbre's consonant intervals captured within `toleranceCents` (default 25c ≈ quarter-tone). `tuningSuitability(edo(12), harmonicSpectrum())` shows 12-TET fits harmonic timbres well; `tuningSuitability(edo(12), bellSpectrum())` confirms poorer fit — the library's core thesis quantified.
- `detectNearestScale(pitches, opts?)` (`src/core/scale.ts`): reverse lookup over 361 named scales spanning world music traditions — scores each by what fraction of its defining cents a pitch list covers, returns ranked matches.
- `optimalChordVoicing(chord, rootHz, spectrum, opts?)` (`src/core/chord-voicing.ts`, new module): brute-forces octave placement per chord member within `opts.registerRange` (default ±1 octave) and returns the voicing minimising `chordDissonance` for the given timbre.
- `sclToTuning(scl, referenceHz?, id?)` (`src/adapters/scala.ts`): the missing inverse of `tuningToScl` — imports a parsed Scala `.scl` as a first-class `TuningSystem`. Preserves ratio degrees exactly as GCD-reduced `Ratio` pitches (not lossy cents), so `parseScl → sclToTuning → tuningToScl → writeScl` round-trips without precision loss.
- `ruri` CLI (`src/cli.ts`, `bin/ruri.mjs`): `info`/`convert`/`render`/`help` commands for batch tuning conversion and audio rendering from the command line — `.scl → .tun`/`.syx`(MTS)/`.ump`(MIDI 2.0)/`.wav`, plus a scale-degree/cents/well-formedness/MOS-L-s-pattern report (`info` prints e.g. `mos-pattern : 5L2s (LLsLLLs)` via `tuningMosPattern`). `runCli(argv, io)` is fs-free and fully unit-testable via an injected `CliIo`; the Node bootstrap (`bin/ruri.mjs`) is the only place that touches real `fs`/`process`, keeping the TypeScript sources free of `node:` imports and `@types/node`.
- `mosPattern(scaleCents, periodCents)` and `tuningMosPattern(tuning)` (`src/core/generate.ts`): adjacent-step MOS analysis in the xenharmonic community's `L`/`s` notation (e.g. diatonic → `5L2s`, pattern `LLsLLLs`). Companion to `isWellFormed` (which tests Myhill's property across all generic interval classes) at the 1-step layer; returns `null` for scales with more than two step sizes.
- MIDI 2.0 UMP adapter (`src/adapters/ump.ts`): `umpNoteOnPitch79`/`umpNoteOff` encode 64-bit MIDI 2.0 Channel Voice Note On/Off with the Pitch 7.9 note attribute (absolute pitch at ~0.195-cent resolution, no bend-range negotiation needed); `umpPerNotePitchBend` encodes per-note pitch bend (bend sensitivity has no spec default, so `bendRangeSemitones` is a required parameter); `chordToUmp`/`tuningDegreeToUmp` bridge the existing `Chord`/`TuningSystem` types; `decodeUmp`/`umpToBytes` support golden round-trip verification and big-endian byte serialization.

### Security

- Resolved the one non-breaking `npm audit` advisory (`js-yaml` quadratic-complexity DoS, GHSA-h67p-54hq-rp68, transitive devDependency) via `npm audit fix`. The remaining 6 advisories (esbuild/vite/vitest chain) only resolve via a breaking vitest 2→4 upgrade, not attempted here; all are devDependencies only — the published package has zero runtime dependencies, so none reach consumers of the library.

### Changed

- **Breaking (pre-1.0)**: `src/core/index.ts` and `src/data/index.ts` no longer re-export the internal generated-function families (`tuningFamilySocratic*`/`tuningFamilyAmbassador*` radar helpers, their 361 named-scale-matcher specializations, and the corresponding `presetFamilySocratic*`/`presetFamilyAmbassador*` preset bridges — ~4,437 functions total). These were implementation-detail bridges never covered by documentation or the README's usage guide; hiding them shrinks the published `.d.ts` surface by two orders of magnitude (`dist/core/index.d.ts`: ~16,700 → 31 lines; `dist/data/index.d.ts`: ~4,700 → 2 lines) with no change to any documented API. `scale.ts`/`presets.ts` are otherwise untouched — internal cross-file imports are unaffected.

### Fixed

- `localMinima`: descending-plateau false positive — plateaus now report once at their first index only when strictly below both differing neighbours; ascending-plateau and end-touching cases are no longer reported.
- Piano `fingerPianoChord`: single-note guard hardened (behaviour unchanged for callers).
- 25 pre-existing bugs in `scale.ts` metric functions, invisible until the full 11,536-test suite could run to completion for the first time (see CI section below):
  - `scaleFifthQualityScore`/`scaleSixthQualityScore`/`scaleSeventhQualityScore` always returned 0 — their target intervals (700c+) exceeded the ±600c range that `Math.min(d, 1200-d)` interval-folding could ever produce, so the match condition was unreachable.
  - `scaleRegisterBalanceV2`/`scaleHighRegisterRatio`/`scaleLowRegisterRatio` computed "register" relative to the pitch set's own local min/max span rather than the absolute octave, so they could never distinguish high from low.
  - `scalePeriodicity` always found each note trivially matching itself via `c % period`, making every candidate divisor pass; now requires a _distinct_ note to match.
  - `scaleDominantPresence` scored an isolated dominant-7th tone as "dominant" even without the V root present.
  - `scaleGravitationalCenter`/`scaleBalancePoint` averaged pitch-classes with a naive linear mean, meaningless on a circle; now use a circular mean with a defined neutral fallback for symmetric/degenerate inputs.
  - `scaleIntervalDensityPeak` used a half-open `[0,200)` binning convention that misclassified an exact 200c step.
  - `scaleReflectionSymmetry`/`scaleTranslationSymmetry`/`scaleInversionSymmetry` had contradictory empty/single-pitch edge-case conventions across independently-authored test blocks (some expected 0, some expected 1); resolved in favor of the mathematically-motivated natural computation — 0 for an empty scale, 1 for a single pitch (trivially symmetric about itself under reflection; self-mapping under translation/inversion only when the pitch is actually a fixed point).
  - `tuningFamilySocraticRadarCompetitionIndexMean` returned 1 instead of 0 for an empty tuning list — its `1 - cooperationIndexMean(...)` formula wasn't guarded for the degenerate case.
  - Plus 10 incorrect test fixtures/thresholds in `scale.test.ts` itself: missing tonic in five "equal-step"/"chromatic" fixture arrays, one unreachable symmetry threshold, and four empty/single-pitch edge-case expectations that had the wrong convention (see above).
- `voiceLeadingDistance`'s sorted-matching branch (used for chords with 5+ voices, above the exhaustive-permutation cutoff) computed a sorted copy of the first chord but never used it, instead pairing the sorted second chord against the _original, unsorted_ first chord. Now correctly pairs the i-th smallest pitch class of each chord. Untested before — no prior test exercised more than 4 voices.
